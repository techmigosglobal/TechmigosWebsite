# TechMigos backend clone kit

This kit produces a single zip that contains everything needed to stand the
TechMigos Supabase backend up in a **different** Supabase project, with the
smallest possible loss of data.

It is generated by `scripts/backend/export-backend.mjs` and restored with
`scripts/restore-backend.sh` from inside the extracted bundle.

## What the bundle contains

```
bundle/
  supabase/
    config.toml            local CLI config (fixed so `supabase` parses it)
    migrations/*.sql       schema, RLS, storage policies, triggers, RPCs
    functions/*/index.ts   admin-users, username-login
  db/
    roles.sql              cluster roles            (full fidelity only)
    schema.sql             schema                  (full fidelity only)
    data.sql               all table data, COPY    (full fidelity only)
    auth.sql               auth schema + password hashes (full fidelity only)
    migration-history.sql  supabase_migrations rows (full fidelity only)
    auth-users.json        Auth users without hashes (degraded mode)
    rest-data/*.jsonl      every public table as JSONL, always written
  storage/
    <bucket>/<object>      every private object, byte for byte
    storage-manifest.json  path, size, content type, sha256 per object
  types/database.ts        generated TypeScript types
  meta/                    deployed function list, secret names/digests,
                           remote migration history, source project details,
                           row-count verification
  MANIFEST.json            step log, row counts, per-file checksums, fidelity
  sha256sums.txt           checksums for every bundled file
  README.md                this file
  scripts/                 restore, data-load, storage, auth, verify helpers
```

Secret values are never bundled. `MANIFEST.json` records the project
reference, URL and row counts only. The exporter writes the service role key
and database URL to `<stage>/secrets.private.env`, which sits **outside** the
zipped `bundle/` directory.

## Fidelity levels

| Level | Requires | Guarantees |
|---|---|---|
| `full` | `SOURCE_DB_URL`, or `SOURCE_DB_PASSWORD` + `SOURCE_DB_REGION` | Schema, roles, all rows, **auth users with password hashes**, storage objects, migration history |
| `degraded` | Supabase CLI session only | Migrations (schema/RLS), storage objects, all public table rows, Auth users without password hashes |

In degraded mode every user keeps their UUID, email and metadata, so
`crm_profiles.auth_user_id` links survive, but each account needs a password
reset because the Auth API never returns password hashes.

## Producing a bundle

```bash
cp .env.backend-export.example .env.backend-export   # gitignored
$EDITOR .env.backend-export                          # add SOURCE_DB_URL (or password + region)
npm run backend:export
```

Output:

- `exports/<label>-<timestamp>.zip` — the deliverable
- `.backend-export/<label>-<timestamp>/bundle/` — the same tree, unzipped
- `.backend-export/<label>-<timestamp>/secrets.private.env` — private credentials, not zipped

Flags: `--label <name>`, `--skip-storage`, `--skip-rest-data`.

`supabase db dump` runs `pg_dump` inside a Docker container, so Docker must be
running, and the first full-fidelity export pulls the Postgres image. A failed
dump never aborts the export: the step is recorded as a warning in
`MANIFEST.json` and `authPasswordHashesExported` / `databaseDumpsExported`
state exactly what the bundle contains.

## Cloning into a new Supabase project

1. Create the new project. Keep the database major version at 17
   (`supabase/config.toml` declares `major_version = 17`).
2. From the new project's **Connect** panel copy the session pooler connection
   string and the service role key; from **Settings > API** copy the
   publishable key.
3. Extract the zip and prepare the target environment:

   ```bash
   unzip techmigos-backend-<timestamp>.zip
   cd bundle
   cp .env.clone.example .env.clone
   $EDITOR .env.clone
   ```

   ```ini
   TARGET_PROJECT_REF=abcdefghijklmnop
   TARGET_SUPABASE_URL=https://abcdefghijklmnop.supabase.co
   TARGET_DB_URL=postgresql://postgres.abcdefghijklmnop:PASSWORD@aws-0-ap-south-1.pooler.supabase.com:5432/postgres
   TARGET_DB_PASSWORD=PASSWORD
   TARGET_PUBLISHABLE_KEY=sb_publishable_...
   TARGET_SERVICE_ROLE_KEY=sb_secret_...
   ```

4. Restore:

   ```bash
   ./scripts/restore-backend.sh
   ```

   The script restores roles, schema, the auth schema, migration history and
   data with `psql` in a Docker container when `db/data.sql` exists. Without it,
   it applies the bundled migrations (`supabase db push`) and then loads table
   data through PostgREST with the recreated Auth users first.

5. Upload storage, deploy functions and verify are part of the same run. Add
   `--skip-storage`, `--skip-functions` or `--skip-auth` to split the work.
6. Repoint the frontend from your repository checkout:

   ```bash
   node scripts/backend/update-frontend-ref.mjs \
     --url https://abcdefghijklmnop.supabase.co \
     --publishable-key sb_publishable_... \
     --old-ref lzlflnjrtxovzrniwmyq
   ```

7. Finish the project-level settings that SQL cannot carry:
   - **Auth > URL configuration**: Site URL plus `/change-password` and
     `/reset-password` redirects.
   - **Edge Functions > secrets**: set every name listed in
     `meta/secrets.json` (`SITE_URL`, `ALLOWED_ORIGINS`, and any provider keys).
   - **Extensions**: enable anything the project used that is not created by
     the migrations.
   - **Vercel**: update `PUBLIC_SUPABASE_URL` / `PUBLIC_SUPABASE_KEY` and the
     `Content-Security-Policy` `connect-src` entry in `vercel.json`.

## Verifying the clone

`scripts/restore-backend.sh` finishes by running
`node scripts/verify-backend.mjs`, which compares the manifest row counts and
storage object counts against the target project and writes
`verify-report.json`. A non-empty `differences` array means the clone is not
complete.

Independent spot checks:

```bash
node scripts/verify-backend.mjs --url https://<ref>.supabase.co --service-key <secret key> --report-only
psql "$TARGET_DB_URL" -c "select count(*) from crm_profiles"
```

## Known limits

- **Auth users**: only the pg_dump path preserves password hashes. Degraded
  mode recreates accounts with temporary passwords.
- **Storage objects**: exported one by one through the Storage API. Very large
  buckets take time; the exporter prints progress per object.
- **Migration history drift**: several migrations were applied through the
  dashboard, so the remote `supabase_migrations.schema_migrations` versions do
  not always match the local migration filenames. The remote history is only
  captured in `full` fidelity (`meta/migration-list.json` and
  `db/migration-history.sql`). When restoring with migrations instead, run
  `supabase db push --include-all`, then `supabase migration repair --status
  applied <version>` for any version the dashboard recorded under a different
  name.
- **Realtime publications and webhooks** are project settings, not schema, and
  must be re-enabled by hand if the original project used them.
- **Vault secrets, Auth providers and mail templates** are not part of the
  database dump.
- **Project reference** is hardcoded in the frontend and in the identity helper
  scripts; `update-frontend-ref.mjs` rewrites those files for you.
